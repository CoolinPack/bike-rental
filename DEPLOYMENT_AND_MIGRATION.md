# Перенос и резервное копирование Bike Rental

## Что изменено

- Новые медиафайлы разделяются по паркам: `parks/{park_id}/images/` и `parks/{park_id}/videos/`.
- Cloudinary продолжает работать; старые URL Cloudinary остаются валидными и могут удаляться прежним способом.
- Добавлен S3-совместимый backend: AWS S3, Cloudflare R2, Backblaze B2 или MinIO.
- Локальное хранилище тоже разделено по паркам, но подходит только для разработки или сервера с постоянным диском.
- При удалении парка URL файлов сначала попадают в постоянную очередь PostgreSQL; фоновая задача удаляет их и повторяет попытки после временных ошибок.
- Миграция `006_tenant_integrity.sql` добавляет составные внешние ключи, чтобы PostgreSQL запрещал связывать записи разных парков.

## ВАЖНО: порядок безопасного обновления

1. Сделайте резервную копию базы Neon. Не начинайте с миграции.
2. Загрузите обновлённый backend и установите зависимости из `requirements.txt`.
3. В Neon откройте SQL Editor и сначала выполните диагностические запросы ниже.
4. Миграция `006_tenant_integrity.sql` уже применена к production-базе Neon. Повторно её не запускайте. Для новой базы сначала сделайте резервную копию, проверьте три счётчика и только затем применяйте миграцию.
5. Для текущего Cloudinary задайте `STORAGE_BACKEND=cloudinary` (или оставьте `auto`, если Cloudinary настроен полностью). Новые загрузки автоматически попадут в папку конкретного парка.
6. Проверьте загрузку и удаление фото/видео на тестовом байке, затем проверьте второй парк.

### Диагностика перед миграцией

```sql
SELECT COUNT(*) AS mismatched_bookings
FROM bookings bk JOIN bikes b ON b.id = bk.bike_id
WHERE bk.park_id <> b.park_id;

SELECT COUNT(*) AS mismatched_expenses
FROM expenses e JOIN bikes b ON b.id = e.bike_id
WHERE e.park_id <> b.park_id;

SELECT COUNT(*) AS mismatched_extensions
FROM booking_extensions be JOIN bookings bk ON bk.id = be.booking_id
WHERE be.park_id <> bk.park_id;
```

Все значения должны быть `0`. Миграция сама повторяет эту проверку и остановится, если обнаружит некорректные связи.

## Настройка хранилища

### Оставить Cloudinary

```env
STORAGE_BACKEND=cloudinary
CLOUDINARY_CLOUD_NAME=...
CLOUDINARY_API_KEY=...
CLOUDINARY_API_SECRET=...
```

Не отправляйте API Secret в чат, GitHub или скриншоты. Храните его только в секретах хостинга.

### Перейти на S3-совместимое хранилище

```env
STORAGE_BACKEND=s3
S3_ENDPOINT_URL=https://...
S3_REGION=us-east-1 # для Cloudflare R2 укажите auto
S3_BUCKET=your-bucket
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
S3_PUBLIC_BASE_URL=https://media.your-domain.example
```

Для AWS S3 `S3_ENDPOINT_URL` можно оставить пустым. `S3_PUBLIC_BASE_URL` должен быть доменом/CDN, по которому браузер сможет получить объекты. Настройте bucket policy/CDN так, чтобы клиентские фото и видео были доступны на чтение. Секретные ключи никогда не добавляйте во frontend.

`STORAGE_BACKEND=auto` выбирает Cloudinary, если он полностью настроен; иначе S3, если заданы его обязательные параметры; иначе локальный диск. Для production лучше задавать backend явно.

## Что нужно знать о переносе уже существующих файлов

Новые загрузки можно сразу направить в S3, а старые Cloudinary URL продолжат отображаться. Это обеспечивает переход без немедленного массового копирования. Однако сами старые объекты не перемещаются автоматически: для полного отказа от Cloudinary понадобится отдельная миграция, которая скачает каждый старый объект, загрузит его в новое хранилище и безопасно заменит URL в JSON-массивах `bikes.photos` и `bikes.videos`. До такой миграции Cloudinary аккаунт нельзя закрывать и нужно сохранять его ключи, если планируется удалять старые Cloudinary-файлы из приложения.

## Резервные копии и переезд на VPS

База и файлы резервируются отдельно. Для PostgreSQL используйте `pg_dump` в custom-формате и храните копию вне сервера. Пример команды из PowerShell (после установки PostgreSQL client tools):

```powershell
$env:DATABASE_URL = "ваша_строка_подключения"
pg_dump --format=custom --no-owner --no-acl --dbname="$env:DATABASE_URL" --file="bike-rental-backup.dump"
```

Восстановление в новую пустую базу:

```powershell
$env:NEW_DATABASE_URL = "строка_новой_базы"
pg_restore --no-owner --no-acl --clean --if-exists --dbname="$env:NEW_DATABASE_URL" "bike-rental-backup.dump"
```

Не запускайте восстановление поверх рабочей базы: `--clean` удаляет существующие объекты. Сначала проверьте восстановление на отдельной пустой базе.

Для медиа настройте versioning/lifecycle и резервное копирование bucket либо периодическую синхронизацию в отдельное хранилище. Один только серверный диск не является резервной копией.

### Рекомендуемая схема

- **Два сервера:** VPS №1 — FastAPI + frontend (если нужно) + PostgreSQL; VPS №2 — S3-совместимое объектное хранилище или MinIO с отдельным диском и резервной копией.
- **Один сервер:** Docker Compose для приложения и PostgreSQL на постоянном SSD; медиа лучше всё равно хранить в объектном хранилище. Если MinIO стоит на том же сервере, это удобно, но не защищает от поломки/потери самого сервера — нужна внешняя копия.

Для будущего переезда сохраняйте отдельно: исходный код и `.env`/секреты, дамп PostgreSQL, полный набор медиафайлов, домены/DNS и настройки Telegram webhook. Не помещайте `.env` в Git или архивы для передачи.

## Ограничения текущего этапа

- Составные внешние ключи усиливают целостность связей между парками, но это не полноценная проверка безопасности или penetration test.
- Очередь `media_cleanup_queue` хранит незавершённую очистку; завершённые записи можно периодически архивировать или удалять после проверки.
- Cloudinary и S3 в этой реализации отдают медиа по публичным URL. Разделение папок/ключей упорядочивает хранение, но само по себе не делает файлы приватными. Для закрытых файлов понадобятся signed URLs или авторизованный proxy.
- Перенос существующих Cloudinary объектов в S3 — отдельная операция; текущая версия сохраняет старые ссылки, чтобы ничего не сломать.
